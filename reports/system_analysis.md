## 2. システム構成

車載Raspberry Piが単眼カメラ画像から白線を検出し、操舵サーボとESCへGPIOのPWM信号を出力する。手動入力はDualSenseをPiへ直接接続し、Linux入力イベントから取得する。WebおよびEven G2には状態を配信し、モード要求も受け付ける。通常の自動走行判断をPCやWeb画面へ往復させる実装ではない。

```text
単眼カメラ → 白線抽出 → 鳥瞰画像の経路点 → 画像誤差PD・先読み
                                                ↓ 自動計画
DualSense → Linux evdev → モード・ギア・停止仲裁 → 独立出力ワーカー
                                                ↓
                           pigpio hardware PWM → サーボ / ESC

車輪回転パルス → 速度換算・表示・ゲイン選択の一部
同一フレーム画像 / マスク / 認識 / 指令 / 処理時間 → 有界診断記録
Web / Even G2 ← 状態サンプル・指令理由 / → モード要求
Wi-Fi・Bluetooth診断 → 独立した観測記録
```

## 3. 白線抽出と経路点生成

### 3.1 動的な白色候補

`adaptive_white.py` 87–123行ではHLSの明度とHSVの彩度を利用する。ROIは元画像の35行目以上200行目未満である。明度ROIの50、99パーセンタイルをそれぞれ床代表値F、上側代表値Uとする。通常の参照値をR=Uとし、条件によって過去の確認済み白線・床参照を補う。S=max(0,R−F)として、明度しきい値と局所差しきい値を次式で求める。

\[
T_L=\operatorname{clip}\{F+\max(5,0.45S),20,245\},\quad
T_\Delta=\operatorname{clip}(0.08S,3,10).
\]

31×31 Gaussianぼかしに対する正の明度差を求め、明度条件・局所差条件・色条件を満たす画素を種とする。隣接する明るい種間で、内部も十分明るい領域を埋め、最後に3×3クロージングを適用する。

色条件はHSV彩度96以下を基本とする。照明の色かぶりで白線も高彩度になる事例への対応として、ROI下半分に一貫した高彩度床がある場合のみ、床より彩度が40以上低く、床色相から16以内、最弱BGR成分と明度が床より各12以上高い画素も許容する。床支持率0.35以上、床彩度192以上等の条件を用いる（同6–48行）。これは学習済み意味セグメンテーションではなく、観測した床と白線のコントラストに基づく規則である。

### 3.2 鳥瞰変換と連続性の検査

主制御227–230行の四点からOpenCVの射影変換行列を構成する。元画像点 `(70,100),(250,100),(320,235),(0,235)` を鳥瞰平面の `(80,0),(240,0),(240,240),(80,240)` に対応させる。これは画素座標の変換であり、実距離への校正値ではない。

`detect_line_from_mask`（1854–2019行）は、変換後マスクの近傍縦ヒストグラムで開始位置を決め、ROIを8段の窓に区切って下から上へ経路点を追う。各窓の候補は白画素数、幅、予測位置からのずれ、前フレームとのずれ、窓間の連続性で選別する。前フレーム点列への二次近似と現在フレームの外挿を併用する。連続した不採用窓が増えると探索を打ち切る。採用点数3以上を`line`とし、信頼度を `clip(0.48+0.08N,0,0.98)` とする。この信頼度は手作りの支持量であり、正解率・確率校正値ではない。

高明度の部分マスクと通常の動的マスクを比較し、確認済みの白線参照が床の色へ落ちないよう保持する。大きな移動で古い探索範囲に収まらない場合は独立した初期状態でも再評価する（1797–1851行）。

### 3.3 遠方観測

`far_preview.py` 60–159行は、通常検出が支持した白線と**同じ連結成分**を元のカメラマスク上で特定し、既存鳥瞰平面の上側へ測定を延ばす。逆射影した横断線を10画素間隔でサンプリングし、鳥瞰y=−190付近まで追う。負のyは通常の240行出力範囲より上に写った路面を表すものであり、地図や未来軌跡の外挿ではない。分岐が曖昧な場合や連結成分が終わる場合は終了する。

基礎経路6点以上、基礎縦幅100画素以上、近傍アンカーの一致等を要求し、近傍と遠方の直線近似の傾き差および近傍直線からの遠方ずれを出力する。角度の単位は画像平面で定義した接線角の度であり、車体の実ヨー角ではない。

## 4. 操舵制御

### 4.1 画像上のPDと形状補助項

経路点を線形補間した位置と、点番号に対する二次近似の位置を混合し、制御点xを求める（主制御2092–2182行）。中心誤差は `e=x_control−160` [px] である。基本の操舵論理値は次の形である。

\[
u_0=10+g\{K_Pe_u+K_Dd_f+0.085h\}.
\]

`e_u`は高周波抑制・連続デッドバンド後の誤差、`h`は点番号に対する二次近似の局所勾配、`g`は経路形状に応じた倍率（最大1.22）である。追加の誤差ブースト係数は現版では0である（2330–2342行）。

微分入力は通常の単位px/sの値をそのまま使わず、実フレーム間隔Δtと基準周期1/30秒を用いて、`d_k=clip((e_u,k−e_u,k−1)(1/30)/Δt,−18,18)` とする。これを係数 `0.65^(Δt/(1/30))` で平滑化する。直線抑制中には、D項が観測された白線位置以上へ先行しないよう余裕幅を制限する（2290–2327行）。従って、係数0.1を単純な連続時間PDゲインと解釈して他システムへ移植できない。

Kpは低出力0.025、高出力0.010、Kdは両者0.10である。車輪換算速度4 km/h以上、または指令出力13–23%の補間を根拠に高出力ゲインへ移り、時定数0.15秒でなじませる（2237–2287行）。指令PWMは実速度の推定値ではなく、回転パルスが欠けたときにゲインが急に2.5倍へ戻らないための代替条件である。

### 4.2 先読みと振動抑制

基礎制御点選択には速度指令に応じたy補間のコードが残るが、保存予選版では `FORCE_FARTHEST_LOOKAHEAD=True` のため、通常は基礎y=116を優先する（207–216、2150–2169行）。追加の `SteeringPreview` は指令28%から48%で強さを増し、基礎点より遠い観測点の位置・方向差を補助操舵へ変換する。通常の補助上限0.40論理デューティ、十分に支持された急曲線では最大1.00、応答時定数0.060秒である（`steering_preview.py` 17–51、200–355行）。これは実車速度からメートル単位の追従距離を計算するPure Pursuitではない。

直線度は直線近似残差、経路点x差分の標準偏差・平均、信頼度の加重和である。小さな誤差に高周波抑制をかける一方、観測誤差の変化が4–10画素へ増えると0.08秒の応答へ切り替える。操舵値には±3論理デューティの範囲制限と、実Δtを基準としたレート制限・EMAを適用する（2351–2455、2208–2234行）。

`ReturnDamping` は近傍・制御点の双方が一貫して中心へ近づき、遠方も直線である場合に限り、既存D項の制限で除かれた戻し成分を一部だけ復活させる。上限は0.10、P成分の25%、正味操舵の50%の最小値であり、正味の旋回方向を反転しない（`return_damping.py` 12–26、65–168行）。画像上の動きから実ヨーレートを計測したものではない。配備記録は物理的追従改善を未確認と明示する。

### 4.3 白線喪失時

知覚状態はTRACK、DEGRADED、LOST、STOPへ遷移する。STOPは連続18フレーム超の不可靠状態を示す内部名であり、必ずしも運転者のSTOPモードではない（2022–2054行）。可靠な操舵を3フレーム保持した後、毎フレーム0.20論理デューティ以下で中立へ戻す。弱い候補から新しい旋回方向は作らない（2544–2601行）。実装上、保持と復帰のこの部分はフレーム基準であり、同じ実時間が保証されるわけではない。

長い白線喪失時にもAUTOを維持して前進出力を残す修正がある（3482–3486行、`CurvePace`の最低値13%）。これはユーザーの「自分で停止する」という運用要求への対応として会話に記録されている。**白線喪失後の継続前進を安全停止として説明してはならない。** 運転者のSTOP/N、緊急停止、ブレーキの仲裁は別に残る。

## 5. 前後進・速度関連処理

自動設定値は原則13–100%であり、前進端と中立の間を正規化した**指令出力率**である。実車速度目標への閉ループ追従ではない。`CurvePace` は経路の近遠接線差、向き、横ずれ、操舵余裕から出力上限を補間し、最終モード仲裁後にAUTO/Dだけへ適用する（主制御2693–2711行、`curve_pace.py`）。

遠方観測対応版では、遠方も十分長く直線と確認できた場合は0.12秒の確認後、最大90ポイント/秒で制限を緩和する。それ以外の通常解除は0.30秒保持、30ポイント/秒である。28–38%の要求範囲で追加制限の強さを変える。遠方カーブの最初の支持された離れ位置から、その近づき具合を画像y座標で評価する（同11–58、78–185、357行以降）。コースの実長や制動距離を予測する処理ではない。

手動ではD/N/RとR2から前進/中立/後退出力を作る。L2は優先し、前進指令履歴がある場合のみ逆側指令でTBLE-04Sの制動機能を使う。ブレーキ履歴は車輪回転の真の方向を検出した結果ではない（`dualsense_control.py` 437–482行）。

## 6. 回転計測と簡易オドメトリ

立上りパルス間隔から瞬時周波数を求め、旧値0.72、新値0.28で平滑化する。設定上は車輪径D=0.06 m、1回転36パルス、速度倍率1として、`v=f·πD/36` [m/s]、`v_km/h=3.6v` とする。0.35秒パルスが来なければ減衰させる（主制御1099–1138行）。独立した距離・時間による校正は保存資料で確認できず、本文では「車輪換算速度」と呼ぶ。

`DeadReckoningState` は指令操舵から最大28度、係数0.5、符号−1を仮定した操舵角を作り、ホイールベース0.26 mの自転車モデル `yaw_rate=v·tan(δ)/L` を積分する（1142–1187行）。走行方向も指令側から与える。測定された実舵角・IMU・絶対位置で補正しておらず、この表示軌跡を実軌跡の真値、地図に対する自己位置推定精度、目標経路追従誤差の実距離評価として利用できない。確認した制御経路ではこの積分位置を操舵や経路計画へ戻していない。

## 7. 手動低遅延化と運転モード

`FastControlOutput` は画像処理と独立した唯一の出力書込者である。入力変更または自動計画変更のイベントで起床し、10 msの周期待機をフォールバックとする。仲裁ロックと物理書込の順序を一体化し、古いAUTO計画が新しい手動/停止を上書きしないようモード世代を照合する（`fast_control_output.py` 18–136、170–231行）。ここでの100 Hzはソフトウェアの定期確認設定であり、PWM50 Hz、カメラフレームレート、無線受信率とは異なる。

DualSense読取は複数軸をSYN_REPORTまでまとめ、同一レポートの途中状態で出力が起きるのを避ける。緊急停止押下はレポート完了を待たず受理する。入力イベントが変化しない保持操作を期限切れにせず、FD読取ループの生存確認と区別する（`dualsense_control.py` 620–670行）。ただしFD生存はBluetoothの物理的な到達保証ではない。

操作割当は×=MANUAL、□=STEER_AUTO、△=AUTO、左X=操舵、R2=アクセル、L2=ブレーキ、L1/R1/Create/Options=緊急停止である。手動系の方向キー上/左/下はD/N/R、AUTO中の上/下は出力設定±5ポイント、左はNである。緊急停止後は全入力を離し、新しい×押下でMANUAL/Nへ復帰する。この復帰操作は参考にしたレーシングカートの運営手順そのものではなく、今回RC向けに追加した仕様である（`IMPLEMENTATION.md`、`ESTOP_RECOVERY.md`）。

## 8. 表示、記録、解析性

Web/G2は出力可否、モード、ギア、接続、知覚状態、指令、中立・緊急停止等の理由を表示する。速度が未取得/古い場合は欠測とし、出力PWMを実測値として表示しない（`telemetry_hud.py` 80–204行）。G2はサーバーで150 ms待つ連続取得を使い、900 ms更新がないと最終状態と表示する。失敗時350 ms待機、HTTP期限1500 msとし、要求IDでモード要求の受理を確認する（主制御HUD_WAIT_SEC、`even_hud_dist/assets/g2-monitor.js` 1–120行）。これらは端末表示の設計値であり、車両制御の遅延保証ではない。

診断記録 `DriveCapture` はAUTO/STEER_AUTOで自動開始し、MANUAL/STOPで確定する。既定10 fps、180秒/1800枚等で分割し、最大6完成ZIP・256 MiBで保持する（`drive_capture.py` 28–46、109–125行）。入力JPEG、3種PNGマスク、同フレームの点・認識・指令・時刻・処理時間・ソースハッシュを対応させる。元画像はJPEGで非可逆であり、PNGマスクは可逆である。保存は全制御周期ではない。TRACK比率は正解ラベルに対する精度でも完走率でもない。

プレビュー処理は最新1件のみを待機させるワーカーへ、診断記録は有界ワーカーへ分離する。ZIPの解析/CSV等の確定は別Pythonプロセス・nice +10へ分離し、記録切替時のPython処理競合を軽減する（`async_visuals.py`、`drive_capture.py`、`drive_capture_finalize.py`、`RECORDING_ISOLATION_REPAIR.md`）。

無線診断は別の `wifi_monitor.py` で、既定2秒ごとに接続リンク、統計、ゲートウェイ応答、入力キュー遅延、HCI診断等を記録する。BluetoothのHCI品質/AFHを実電波スペクトル、ロス率、干渉源同定と呼んではならない。`pico_radio_monitor_20261115/` のPC接続PicoによるAP走査は別観測位置の測定である。
